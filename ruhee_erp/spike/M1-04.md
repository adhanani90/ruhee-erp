## Rate precision source

Installed sources (no changes made):

- POS Awesome `frontend/src/posapp/utils/erpnextCurrency.ts:priceListToSelectedCurrency`
  computes `amount * getPlcConversionRate(context) / getConversionRate(context)`.
  `frontend/src/posapp/composables/pos/items/useItemCurrency.ts:useItemCurrency`
  defines `applyCurrencyConversionToItem`, which calls that formula and applies
  `flt(converted_rate, context.currency_precision)` before assigning both `rate`
  and `price_list_rate`.
- ERPNext `erpnext/accounts/doctype/sales_invoice/sales_invoice.json`, DocField
  `conversion_rate`: Float, **precision "9"**. This is declarative metadata, not
  a function. `erpnext/setup/doctype/currency_exchange/currency_exchange.json`,
  DocField `exchange_rate`, also declares **precision "9"**.
- Frappe `frappe/model/document.py:Document.precision` resolves the DocField via
  `frappe/model/meta.py:get_field_precision`, which prioritizes explicit field
  precision over system defaults. The saved invoice resolves this to **9**.
- Frappe `frappe/database/schema.py:get_definition` uses field precision as the
  decimal scale when defining Currency/Float/Percent columns;
  `frappe/database/mariadb/database.py:MariaDBDatabase.setup_type_map` supplies
  the numeric type mapping. `MariaDBDatabase.get_column_type` confirms both
  live columns are **decimal(21,9)**. Raising only a UI/system float precision
  would not increase these columns' capacity or replace the stored reciprocal.

## Handoff note for #6: candidate mitigations, not implemented

These are candidates for M1-05 investigation, not selected designs or proven fixes.
No rate record, field precision, CDF price list or calculation path is changed in
#5. All candidates must retest the two discrepancies and C3-C5 using the store rate
record, plus saved/reloaded values, GL, offline sync, payments and original-rate
returns. New stored rate values must not rewrite submitted documents (I8).

| Candidate | Potential benefit | Trade-offs / work still to verify in #6 |
| --- | --- | --- |
| Higher reciprocal precision | A sufficiently precise 1/2300 can remove the observed two-decimal price error and cent error at this bill size with fewer formula changes. | Must increase source-rate and downstream document field/storage precision consistently, migrate the schema through app-owned settings, and create a fresh rate from the direct rate; padding the existing 0.000434783 adds no accuracy. Explicit field precision means a global setting alone is insufficient. Check payment/return fields, JS/offline serialization, caches and every recalculation. A finite reciprocal still has an error bound; a larger scale at a fixed total column width reduces integer capacity. No claim that a particular scale is sufficient for all bill sizes. |
| CDF item pricing | An exact CDF Item Price can supply 230,000 FC without converting the USD unit price through the reciprocal. | Fixes the line-price symptom only: with the current invoice conversion_rate, exact 23,000,000 FC still posts $10,000.01. Maintaining a second catalogue, or generating effective CDF prices per store-rate revision, adds synchronization/offline/versioning work and must keep the USD price x base-rate rule. Requires a separate solution for GL conversion. |
| Compute from direct store base rate 2300 | USD price x 2300 gives the exact requested line; CDF amount / 2300 gives the requested USD totals for these examples without first quantizing the reciprocal. | Frontend-only multiplication does not fix native GL: ERPNext still recalculates base amounts using conversion_rate. Need verified hooks/adapters that use the referenced store record consistently for pricing, base totals, payment allocation, saved/reloaded invoices and offline replay. Keep that record immutable and reuse the original on returns. Establish how to coexist with native recalculations; manually overwriting submitted GL or adding corrective rounding is not a candidate. |

## Reproduce

M1-03's baseline must exist and `check_rate` must pass. From `~/frappe-bench`:

```bash
bench --site dev.localhost execute ruhee_erp.spike.posting_model.run
```

Each successful run adds eight invoices and a shift. It copies New Depo into its
own `M1-04 New Depo` profile, enables multi-currency/partial/credit sales, preserves
Sales Invoice mode and immediate stock updates, and disables background submit.
The dedicated profile's stock-availability block is off to use M1-03's negative
stock baseline. This is feasibility evidence with negative stock, not stocked-store
acceptance. All profile changes live in the script; existing differing settings
stop the run instead of being overwritten. It creates an invented cashier with a
random PIN, verifies it using the normal endpoint, locks the terminal and disables
that cashier on success. No PIN is logged. It never changes daily rates, item
prices, precision settings or submitted invoices. The original New Depo profile
and Claude Code's worktree/site are untouched.

Local validation: baseline rate check PASS; complete probe PASS, including
submitted document type, stock quantities, unchanged ledger snapshots at close,
invoice $50 balance and Accounts Receivable $50 balance assertions. Two preliminary
invocations failed during harness development (terminal locked, then incorrect
closing response unpacking); both were corrected without patching installed apps.
An earlier successful eight-bill run remains as invented local data; this evidence
is from the final run with report extraction and close snapshots.
